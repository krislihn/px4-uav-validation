## 1. 脚本与数据(优先级最高)

### 1.1 alt_err 的口径 —— [已确认: 第三参数是绝对高度]
- **结论(2026-10-18):** `goto_location()` 第三个参数是绝对高度(AMSL)。脚本传入相对 10 m,
  而 SITL home 海拔约 488.27 m,等于要求机体降到地下,因此落地后 relative_altitude_m 约为 0,
  alt_err 约为 10。证据: `logs/test_runs/2026-10-16_alt_probe.csv`
  (rel 0.00 -> 2.32 -> 0.00; abs 488.27 -> 490.58 -> 488.19)。
- **修复:** `goto_location(lat, lon, home_abs + alt, 0)`,其中
  `home_abs = position().absolute_altitude_m`(提交 `b268643`)。
- **修复后验证:** 三次全流程运行,alt_err = 0.08/0.01/0.00、0.02/0.11/0.10、0.06/0.00/0.01 m。
  运行输出见 `logs/test_runs/2026-10-18_mission_run.txt`,结果见 `flight_results.csv`。

- 现象: `logs/2026-10-13_flight_results.csv` 三个航点的 alt_err 分别为 9.99 / 10.05 / 9.96 m, 几乎等于航点设定高度 10.0 m。
- 推断: 脚本里 alt_err = |relative_altitude_m - 10.0|, 反推三个时刻的 relative_altitude_m 约为
  0.007 / -0.047 / 0.039 m, 也就是机体当时几乎贴在地面高度上。
- 可疑原因: `scripts/waypoint_mission.py` 调用 `drone.action.goto_location(lat, lon, 10.0, 0)`,
  该参数的第三位是绝对高度(AMSL), 而脚本随后拿 relative_altitude_m(相对起飞点)与它比较,
  两处口径不一致。
- 这意味着: 这份 CSV 里的 alt_err 不能解释成"高度控制误差 10 米",
  它很可能记录的是"指令高度与实际位置的口径不一致"。
- 如何验证: 重跑任务, 从起飞到降落连续记录 relative_altitude_m 与绝对高度, 画高度-时间曲线。
- 影响: 在验证通过之前, 阶段 2 的自主飞行任务判定为"未通过", 不得写入简历或技术报告。

### 1.2 等待全部依赖固定 sleep, 没有状态验证与超时 —— [已确认]

- `scripts/waypoint_mission.py` 在 arm / takeoff / goto 之后统一用 `await asyncio.sleep(N)` 等待。
- 违反方案要求: "所有等待设置超时, 捕获异常; 程序不仅发指令, 还要验证实际结果"。
- 具体风险: 解锁是否成功、是否真的爬升到目标高度、是否真的到达航点, 全部没有检查。
- 改进方向: 每次等待改成"轮询目标状态 + 超时上限", 超时即明确报错退出。

### 1.3 每个航点只采样一次 —— [已确认]

- 到达判定是在 sleep 结束后读取一次位置。
- 单点采样无法区分"已稳定悬停在航点"与"刚好路过"。
- 改进方向: 连续采样一段时间, 用均值、标准差、95 百分位描述(对应阶段 4 的指标)。

### 1.4 结果文件覆盖写, 且不在 logs/ —— [已确认]

- `open('flight_results.csv', 'w')` 使用覆盖模式, 写到脚本当前工作目录。
- 违反方案要求: "每次运行使用不同文件名, 避免覆盖原始数据"。
- 改进方向: 输出到 `logs/`, 文件名带日期与任务编号, 不覆盖已有文件。

### 1.5 冗余 import —— [已确认]

- `from mavsdk import telemetry` 未被使用, 不影响运行, 清理时删掉即可。

### 1.6 磁盘被 /tmp/px4.log 写满 —— [已确认, 已处理]

- 现象: `telemetry_logger.py` 写 CSV 时抛 `OSError: [Errno 28] No space left on device`。
- 原因: 仿真以 `HEADLESS=1 nohup make px4_sitl gz_x500 > /tmp/px4.log 2>&1 &` 后台运行;
  PX4 的 `pxh>` 提示符在非终端环境下会持续写入 stdout, 55 分钟写出约 9 GB。
- 处理: 停止仿真, 删除 `/tmp/px4.log`, 并清理 2026-10-13/16/17/21 的旧 `.ulg`(约 3.3 GB)。
  处理前 `/` 100% 满; 处理后约 12 GB 可用。
- 预防: 仿真在交互式终端里前台运行, 不要把输出重定向到文件长期后台运行;
  每次启动前用 `df -h /` 看一眼剩余空间。
- 证据: 2026-10-24 处理记录(本条目)。
